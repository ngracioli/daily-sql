## 🚀 Project Overview & Scope
**DailySQL** is an interactive coding platform where developers practice SQL by solving daily query challenges.
1. **Interactive Layout:** The user interface features a split layout: challenge description, table schemas, and data viewers on the left; Monaco-based SQL editor and execution consoles on the right.
2. **Context-Aware Autocomplete:** The Monaco SQL editor features customized auto-completion suggesting standard SQL keywords alongside challenge-specific table and column names dynamically.
3. **Rollback-Only Sandbox:** User-submitted queries are sent to a sandboxed PostgreSQL instance where they execute inside an isolated transaction. The results are compared for structure/order/data against the official solution, after which the transaction is instantly rolled back.
4. **Output Visualization:** Users inspect execution results under three tabs:
   - **Initial Data**: Initial database mock records.
   - **Expected Result**: Column structure and rows expected by the solution.
   - **Your Result**: Columns and data actually generated by the user's execution (making schema/data mismatches immediately clear).

## 📚 Key Guidelines (From `docs/`)

AI Agents must review the documentation in `docs/` before making modifications. Here are the core specifications:

### 🧩 1. Code Organization & Modular Design (`docs/code-organization/`)
We follow a variation of **Feature-Sliced Design (FSD)**:
* **Features (`src/features/`)**: Self-contained domain areas. Folders are structured as:
  - `ui/` - Pure UI render components.
  - `model/` - Logic, state management, static constants, and helper functions (e.g. Monaco autocompletes).
  - `api/` - Feature-specific endpoint calls.
  - *Rule:* Do NOT leak internal Monaco or database logic directly inside components. Put them inside `model/`.
* **Shared UI (`src/shared/ui/`)**: Reusable UI atoms, molecules, or organisms following **Atomic Design** (`Table.tsx`, `Tabs.tsx`, etc.).
* **Widgets (`src/widgets/`)**: Combine features and shared components into reusable page sections (e.g., `ProblemPanel.tsx`, `EditorPanel.tsx`).

### 🧱 2. UI Component Library (`docs/components/`)
* Do not build ad-hoc utility designs. Follow CSS tokens and conventions from [css-tokens.md](file:///home/ngracioli/www/projects/DailySQL/daily-sql/docs/style-guide/css-tokens.md).
* Keep components simple, clean, and accessible.

### 🛡️ 3. Security, Sandbox & API (`docs/architecture/`)
When handling user query execution, strict guidelines must be followed:
1. **Low-Privilege Role:** Sandbox executions run under `daily_sql_runner` in PostgreSQL.
2. **Transaction Sandboxing:** All queries must execute inside a `BEGIN; ... ROLLBACK;` block to ensure no state pollution.
3. **Execution Limits:** Runtimes are restricted via `statement_timeout = 1000` (1 second).
4. **Sanitization:** Run inputs through SQL sanitizers to reject administrative, alter/drop, or catalog commands.
5. **No Solution Leakage:** The correct SQL solution (`solutionSql`) must never be sent to the client. Verification and comparison happen strictly server-side.
